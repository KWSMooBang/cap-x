# cap-bg Baseline (CaP-Agent0, ensemble off)

The cap-bg baseline uses the CaP-Agent0 settings (`env_configs/libero/franka_libero_cap_agent0.yaml`) with the
parallel ensemble **off**. Image differencing (VDM) and multi-turn are on. The CaP-Agent0 YAML itself is left
unchanged as the record of the paper settings.

## Configs

All baseline configs are generated by `scripts/gen_capbg_baseline_configs.py`. Do not edit them by hand. Change
the script, then rerun it:

```bash
python scripts/gen_capbg_baseline_configs.py          # writes env_configs/capbg_baseline/
python scripts/gen_capbg_baseline_configs.py --check  # exit 1 if a file is stale (also run by tests/)
```

| Config | Benchmark |
| --- | --- |
| `env_configs/capbg_baseline/libero_pro/franka_libero_object_swap_0.yaml` | LIBERO-PRO `libero_object_swap` task 0 (same task as CaP-Agent0) |
| `env_configs/capbg_baseline/libero_mem/task_<NN>_<slug>.yaml` | LIBERO-Mem tasks 0–9 (0-based `task_id`; e.g. `task_06_swap_bowls` = `KITCHEN_SCENE1_7`) |

Every config sets these values explicitly instead of relying on defaults:

| Key | Value |
| --- | --- |
| `use_parallel_ensemble`, `use_multimodel` | `false` |
| `use_img_differencing` | `true` |
| `use_visual_feedback`, `use_video_differencing`, `use_wrist_camera` | `false` |
| `record_video`, `save_multiturn_prompts` | `true` |
| `max_tokens` | `32768` (coding model and VDM; upstream default 20480, see below) |
| `prompt`, `multi_turn_prompt` | copied verbatim from the CaP-Agent0 YAML |
| `apis` | `FrankaLiberoApiReducedSkillLibrary` |
| `api_servers` | pyroki 8116, contact_graspnet 8115, sam3 8114 (same as CaP-Agent0) |
| low-level env | `privileged: false`, `max_steps: 8000`, `control_freq: 20` |
| `trials` / `num_workers` | 50 / 10 (override with `--total-trials` / `--num-workers`) |

`FrankaLiberoApiReducedSkillLibrary` also works with `FrankaLiberoMemEnv`, because it is a `FrankaLiberoEnv`
subclass with the same cameras and control methods. The API only uses `get_observation` and
`move_to_joints_*`. Its SAM3, GraspNet, pyroki and Molmo clients are HTTP clients, so they need no server when
the API is created. Each server only has to be up when the generated code calls it.

**`max_tokens`:** the YAML `max_tokens` key sets the per-reply token limit for both the coding model and the
VDM; `--max-tokens` on the CLI overrides it, and without either the original default 20480 applies. The
baseline uses 32768, not 20480: on Nebius reasoning tokens count against the limit, and in the LIBERO-Mem 10×5
pilot (`max_tokens` 20480) Kimi-K3 replies hit it often (17 replies ran with an unclosed code fence and one
ended a trial with an infinite loop). Checked on Nebius (2026-10-30): both Kimi-K3 and Qwen3.8-27B accept it, and
a long Kimi-K3 reply ran to exactly 32768 completion tokens before stopping with `finish_reason: length`. Nebius
does not reject larger values either, so acceptance alone says nothing about the server-side cap.

**Ensemble ablation:** use the same configs and turn the ensemble on from the CLI with
`--use-parallel-ensemble True --use-multimodel True`.

## venvs

The `libero`, `libero-mem` and `molmo` (vllm) extras are mutually exclusive, so use one venv for each:

```bash
uv venv .venv-libero --python 3.12 && source .venv-libero/bin/activate
uv sync --active --extra libero --extra contactgraspnet          # LIBERO-PRO

uv venv .venv-libero-mem --python 3.12 && source .venv-libero-mem/bin/activate
uv sync --active --extra libero-mem --extra contactgraspnet      # LIBERO-Mem

uv venv .venv-molmo --python 3.12 && source .venv-molmo/bin/activate
uv sync --active --extra molmo                                   # Molmo2-8B vLLM server only
```

## Molmo server (start it separately)

The API's `point_prompt_molmo` calls a Molmo2-8B vLLM server at `http://127.0.0.1:8122/v1`. The molmo extra
cannot be installed in the libero venvs, so the server is not in `api_servers`. Start it from `.venv-molmo`
before launching:

```bash
.venv-molmo/bin/python capx/serving/vllm_server.py --model allenai/Molmo2-8B --port 8122 \
    --max-model-len 16384 --max-num-batched-tokens 16384 --log-file logs/molmo.log &
```

One image is about 8134 tokens, so vLLM fails to start with its default limits. Keep the two `16384` flags. Use
`--gpu-memory-utilization` if the server shares the GPU with SAM3 and GraspNet.

## Rendering

- **LIBERO-PRO:** on GPU nodes, `MUJOCO_GL=egl` works (it is also the default set by `launch.py`).
- **LIBERO-Mem:** on GPU nodes, use `MUJOCO_GL=egl PYOPENGL_PLATFORM=egl`. LIBERO-Mem's robosuite 1.4.1 EGL
  context fails with PyOpenGL 3.1.6 on Python 3.12; `capx.envs.simulators.libero_mem` patches it on import
  (`patch_robosuite_egl_context`). Without a GPU, use OSMesa with `NUMBA_DISABLE_JIT=1` (see
  `docs/memory-benchmarks.md`): `MUJOCO_GL=osmesa PYOPENGL_PLATFORM=osmesa NUMBA_DISABLE_JIT=1`. That path is
  much slower (CPU rendering, no JIT) and is meant for smoke checks, not evaluation.

## Trial timeout

Each trial attempt has a wall-clock budget (`trial_timeout_s`, default 1000 s, counted from after `env.reset()`)
and is retried on timeout up to
`max_trial_retries` times (default 3). Both can be set in the YAML or on the CLI (`--trial-timeout-s`,
`--max-trial-retries`). For baselines, use `--max-trial-retries 1`: with an enforced timeout, a retry re-rolls a
slow trial and biases the success rate up. The budget includes model latency, so a timeout mixes slow API calls
with task failure; report timeouts separately.

Known limitations of the SIGALRM timeout (the robust fix is killing the worker process from outside):

- After the deadline the alarm re-fires every 2 s, so it can interrupt cleanup code (`finally` blocks) in the trial.
- Generated code that loops forever inside a bare `except:` can still swallow every alarm.

A timed-out trial still saves its video (per-turn videos plus `video_combined.mp4`, including the turn that was
cut off) from the frames recorded so far; if no frames were recorded, no video is written.

## Init states

LIBERO-Mem tasks 0, 6, 7 and 8 use upstream init states; tasks 1, 2, 3, 4, 5 and 9 use the generated sets in
`capx/integrations/libero_mem/init_states/` (see `docs/memory-benchmarks.md`). Each trial records `init_source`, and
`analyze_pilot.py` reports success per init source, so report the two groups separately. Regenerate with
`MUJOCO_GL=osmesa PYOPENGL_PLATFORM=osmesa NUMBA_DISABLE_JIT=1 python scripts/gen_libero_mem_init_states.py --tasks 1 2 3 4 5 9 --num 50`
(about 4 GB RAM per process; reruns with the same seed give the same states).

## Step cap

`max_steps` in the low-level env config is the step budget; the robosuite horizon is built from the same value.
`FrankaLiberoEnv` (and LIBERO-Mem) raises `EpisodeTruncated` (a BaseException, so generated code cannot swallow
it) before a sim step would exceed it. The sandbox stops the code, `env.step` reports `truncated` from the env's
own step count, and the trial ends with a final `all_responses.json` entry
`{"decision": "truncated", "reason": "step_cap"}` and `Truncated: True` in `summary.txt`.

## Multi-turn decisions

The original harness treated any reply without the literal `REGENERATE` as FINISH, so new code written without
the keyword (or in Kimi-K3's raw tool-call format) was dropped and the trial ended. Replies are now classified
by `parse_multi_turn_decision` in this order: `REGENERATE` keyword (original behavior, with the code after it
normalized the same way); a fenced code block (also an unclosed one cut off by the token limit) or a tool-call
`code` argument means regenerate, unless `FINISH` comes after the last code (e.g. quoting code that already
ran), which finishes so that code is not run twice; `FINISH` with no code means finish; an empty reply is
queried once more and finishes if it is empty again; anything else finishes. Each multi-turn entry in
`all_responses.json` records `decision_source`, `decision_flags` (`finish_with_code`, `finish_after_code`,
`unclosed_fence`) and `legacy_decision`, so runs can report format violations and how often the decision
differs from the original parser. Every model reply entry also records `finish_reason` and `usage`:
`finish_reason: length` means the reply hit `max_tokens`, and on Nebius reasoning tokens count against it (a
reply cut during reasoning comes back with empty content).

A reply with `finish_reason: length` is never executed or parsed (the initial code and multi-turn decisions
alike): the same prompt is queried once more, and the entry records `truncation: retry` and the first reply's
`truncated_first_usage`. If the second reply is cut off too (`truncation: skip`, `decision_source:
truncated_skip`), no code runs; the next turn runs nothing and its decision prompt shows "Your previous reply was
cut off by the output token limit and was not executed. Reply more concisely." in place of the console stderr.
That turn counts toward the turn limit, so repeated truncation cannot loop forever. The `unclosed_fence` flag
therefore only appears when the API reports no `finish_reason` or a reply ends in an open fence for another
reason.

**Goal in decision prompts (differs from the original cap-x):** the original harness filled
`{libero_environment_goal}` only in the first prompt, so every decision prompt said `Goal:
{libero_environment_goal}`. `_patch_libero_goal` now also fills the env's own prompt (from the unfilled template,
restored on `reset()`), so all memory modes see the same goal line in every prompt; the first prompt and the VDM
task description are unchanged.

## Memory conditions (`memory_mode`)

The same baseline configs run every memory condition. Choose the condition on the CLI and leave the generated
YAMLs as they are (`memory_mode` is not in them, so it defaults to `none`):

| `--memory-mode` | What the decision prompt gets |
| --- | --- |
| `none` (default) | The cap-x baseline. Every prompt is byte-identical to the harness before memory existed (`tests/test_memory_mode.py` checks this against a recorded fixture). |
| `vdm_history` | The VDM descriptions of all previous turns, as `turn k: ...` (unstructured text memory). The current turn's description is already in the VDM block, so the history leaves it out. |
| `bg_oracle` | A Belief Graph built from LIBERO-Mem **simulator ground truth** (`capx/belief/`): progress over the BDDL goal steps, object positions and supports, location-change events, plus the S2 / S5 signals below. This is an upper bound, not a deployable method. |
| `bg_est` | A Belief Graph **estimated** from what the robot can use (cameras, robot state, API calls, VDM, task language), with S1 / S2 / S4 / S5. See [Estimated Belief Graph](#estimated-belief-graph-bg_est). |
| `bg_est2` | `bg_est` v2: the VDM reads marked images and answers `Observe:` statements, the code declares `# Subtask` / `# Effect`, goal steps hold only newly true predicates, a subtask layer, S1–S5, `belief_trace.jsonl`. See [Estimated Belief Graph v2](#estimated-belief-graph-v2-bg_est2). |

The memory block goes after the VDM description and before the REGENERATE / FINISH instructions. Options (CLI
flag or YAML key of the same name; CLI wins):

| Key | Default | Meaning |
| --- | --- | --- |
| `memory_max_chars` | 3000 | Budget of the memory block. `vdm_history` drops the oldest turns. `bg_oracle` drops the oldest events, then shortens and finally leaves out the objects line, but never cuts the Progress and Signals lines (`memory_state.over_budget` marks when those alone exceed the budget). |
| `memory_signals` | `S2,S5` | `bg_oracle` signals (`none` turns them off). S2: an executed turn left the number of remaining steps unchanged. The prompt says "no progress this turn" and asks the model to rethink. S5b: every step is verified complete. The prompt says so, and the model still decides FINISH (the harness never ends a trial by itself). S5a: a FINISH while steps remain is rejected and the same prompt is asked again with the reply and the remaining steps appended. That answer stands. |
| `memory_max_finish_rejections` | 1 | S5a rejections per trial. |
| `memory_in_initial_prompt` | true | `bg_oracle` / `bg_est` / `bg_est2`: also append the turn-0 graph to the first code-generation prompt (`bg_est2` appends its M4 rules either way). |

Example (LIBERO-Mem task 6, oracle condition):

```bash
uv run --no-sync --active capx/envs/launch.py \
    --config-path env_configs/capbg_baseline/libero_mem/task_06_swap_bowls.yaml \
    --memory-mode bg_oracle --output-dir outputs/capbg_bg_oracle/task_06_swap_bowls ...  # model flags as above
```

Use a separate `--output-dir` per condition. The generated YAMLs all point to the same default directory.

A turn that ran no code (`truncated_skip`) still updates the memory, so its text keeps the current turn
number, but it never fires S2. The next executed turn is compared with the last executed one.

Logs in `all_responses.json`: the initial entry has `memory_mode`, `memory_initial_text` (exactly what was
appended to the first prompt, or null) and `memory_state`. Every decision entry has `memory_mode`, `memory_text`
(exactly what the prompt got), `memory_signals` (`[{id, reason, text}]`), `memory_state` (`bg_oracle`: `done`,
`remaining`, `overshot`, `known`, `over_budget`) and `s5_rejected`. A rejected FINISH also records `s5_rejection`,
`s5_first_reply` (the rejected reply with its parse metadata) and `s5_rejection_prompt_tail` (the two appended
messages). The entry's decision fields describe the second answer.

`bg_oracle` reads ground truth through the harness's own `env.low_level_env` reference. Generated code still
gets no memory or env object (exposing a belief API to code is out of scope).

## Estimated Belief Graph (`bg_est`)

`bg_est` builds the same kind of graph as `bg_oracle` (`capx/belief/`) from information the robot can actually
use, so the gap between the two separates the memory effect from the effect of being given the true state.

**Uses:** the agentview RGB-D image with intrinsics and extrinsics (what `get_observation()` returns), the
end-effector pose and gripper opening (`robot_cartesian_pos`, `robot_joint_pos`), the API calls the generated code
made (arguments, return, timing), VDM replies and the task language.
**Never uses:** simulator object poses or sim state, BDDL objects or predicates, LIBERO-Mem's progress tracker
(`memory_state`), `task_completed`. Those only feed the oracle shadow in the evaluation logs.
`tests/test_belief_est.py::test_estimation_path_reads_no_sim_state` runs the estimator against an env stand-in
that fails on any attribute other than `get_observation` and `_sim_step_count`.

Modules: `goal.py` (task language -> steps), `perception.py` (detections -> 3D), `hooks.py` (API call records),
`verify.py` (verification VDM), `estimator.py` (association, geometry, fusion, events, progress, S1/S4 inputs).

### Objects and aliases

Object categories come from the task language through a fixed vocabulary (`perception.VOCABULARY`; "bowl" ->
SAM3 prompt "black bowl", "cream cheese" -> "cream cheese box", ...), at most `max_categories` (default 5), in
order of mention. Each category is one SAM3 text-prompt call on the agentview RGB. Each instance mask (score >= 0.4,
duplicates with mask IoU > 0.5 removed) is lifted to 3D with depth, intrinsics and extrinsics in the robot base frame,
the same frame as the generated code. Center = median point, size = 5-95 percentile extent per axis.

Aliases are `<category>_<letter>`. At turn 0, instances of a category are lettered in order of their base-frame
y (robot's right first), ties by x: `bowl_A` is the bowl furthest to the robot's right. Turn 0 merges
`init_passes` (2) detection passes of the static scene, which makes a missed object less likely. An object first
seen later gets the next free letter. Aliases never change once given.

**Data association** (per category, per turn): one global Hungarian assignment over all tracks and detections of
the category, on the 3D distance between each track's predicted position and the detections. The held object is
predicted at the EEF. Pairs beyond `gate_dist` (0.10 m) cannot be assigned in this step, so a long crossing pair
never pushes out a match inside the gate. In a second step, and only there, the
leftover detections are re-matched to leftover tracks of the same category within `rematch_dist` (0.50 m). New
nodes are created only after that. A track left unmatched keeps its last position and edges (source `mem`,
no decay). Detections of different categories within `dedup_dist` (0.01 m) count as one object.

### Relations from geometry

With `d` = xy distance of the centers, `dz` = z(x) - z(y) and `r` = half the larger xy extent of y (at least 3 cm):
- `On(x, y)`: `d < r` and `0 < dz < 0.10` m. A bowl resting on a LIBERO plate is about 0.018 m above it (centres).
  A bowl tilted onto the plate rim, which is not On for LIBERO, sits level with it and comes out near P 0.5.
- `In(x, y)` (y a container category: basket, tray): `d < r` and `dz` within y's height (-h/2 - 0.02, h/2 + 0.03).
- The margin `m` is the smallest of `(r - d) / max(r/2, 2 cm)` and the z margins / 1 cm. P = 0.5 + 0.47 min(|m|, 1)
  when it holds, 0.5 - 0.47 min(|m|, 1) when not. Clear cases are 0.97 / 0.03 and borderline cases come out near 0.5.
  If y was not seen this turn (position from memory), the confidence is halved.
- `inhand`: from the gripper. After the last gripper call was `close_gripper` and the opening is above
  `grasp_threshold` (0.05), the tracked object nearest the EEF (within `grasp_radius`, 0.10 m) is in hand
  (P 0.97 if seen there, else the hook expectation stays). Every other object is not in hand (0.03).
  An object in hand is on / in nothing.
- `On(x, table)`: only from geometry. The table height is the lowest object bottom (center z - half height) seen at
  turn 0. It holds when x's bottom is within `table_tol` (0.03 m) of that height, with P scaled by the margin as
  above and capped at 1 - P of x's best support (a bowl on a thin plate is near table height too). Without a
  table height (nothing seen at turn 0), or for an object not seen, it is never assumed. An object with no true
  location relation is shown as `location unknown`.

### Hooks and expected effects

`close_gripper`, `open_gripper`, `move_to_joints`, `goto_pose` and `goto_home_joint_position` are wrapped in the code
sandbox (`ApiCallRecorder`). A wrapper records the sim step and the EEF / gripper before and after the call. It passes
the arguments, return value and exceptions through unchanged. All recording (argument text, array copies, robot
state reads) is inside try/except, so a recording failure only loses the record. From the records, in order:
- `close_gripper` with the opening still above `grasp_threshold`: the nearest tracked object is held, expected
  `inhand` (P 0.7, source `exp`). A `close_gripper` that closes fully while a tracked object is within
  `grasp_radius` of the EEF is a missed grasp (S1, naming the nearest object as the likely target). With no object
  nearby there is no signal. It counts as picked up (`in gripper` event) once the EEF has risen `lift_min`
  (0.03 m) while holding.
- `open_gripper` while holding: expected `On(x, s)` (or `In`) with `s` the highest tracked object under the EEF,
  else `On(x, table)`. The held object's predicted position moves to the EEF.
- A motion during which the gripper closes fully while holding: the object was dropped (S1).

### Fusion

Per edge, highest first: geometry / gripper (`obs`) > verification VDM (`obs`, P 0.9 / 0.1) > this turn's expectation
(`exp`, 0.7 / 0.3) > memory (`mem`, P kept) > prior (0.5). When geometry and the VDM disagree on whether an edge
holds, both go into the log (`conflicts`). The one further from P=0.5 wins, geometry on a tie, so a clear
geometric observation (0.97) beats the VDM (0.9) and the VDM beats a borderline one.

The verification VDM is called once per turn with the agentview images before and after the turn and a numbered list:
this turn's expected effects that should hold, plus goal predicates whose geometry is missing or between 0.3 and 0.7
(at most `max_hypotheses`, 8). Objects are named by alias and the pixel their estimated position projects to.
Answers are true / false / not_visible as JSON. A reply that does not parse is ignored.

### Events and progress

An event is a change of an object's location label. Events from hooks come first, in call order (`exp`). Then come
changes between the last hook state and the observed end-of-turn state (`obs`, or `vdm` if the VDM decided).
A hook event that the end-of-turn observation confirms is labelled `exp+obs`.

The goal is parsed once, after the turn-0 perception: the coding model, text only, gets the task language and the
object list, and returns JSON steps over aliases (`goal.py`). It may give alternative orders (`or`) and repeats
(`"repeat": N` for "N times"). A bad reply is asked once more with the error; if it fails again, progress is
unknown. `goal_source: bddl` (diagnostics only) uses the BDDL goal with sim names mapped to aliases instead.

Progress counts a step when all its predicates hold in a location snapshot after not holding in an earlier snapshot
since that step was last counted. This is tracked per goal step from the first snapshot on, so a step that turns
true right after, or together with, the previous step is still counted. LIBERO-Mem's tracker counts the same way: the subgoal has to be false before it can count
again. Snapshots are taken after every hooked call and at the end of the turn. So "pick the bowl up and put it back
on the plate" counts once even though the end-of-turn state did not change. The state alone cannot show a
repetition: a turn that moved the bowl without hooked calls counts nothing. A completed goal whose last step is
observed undone at the end of a turn is marked overshot, as in LIBERO-Mem.

A count made on a hook snapshot is **pending** until an observation at the end of a turn (geometry, gripper or VDM)
confirms the step's predicates with P >= 0.7. A count is withdrawn only for P <= 0.3; anything in between keeps it
pending. If the observation contradicts it (for example the bowl was put back but rolled off
the plate), the count is withdrawn: the counter is rerun from the start of the turn without that snapshot and the
ones after it, and S1 is raised. A count on the end-of-turn snapshot that the observation contradicts takes the
same path: it is withdrawn and S1 is raised, it is never left pending. If the object was not seen at the end of the turn, or was picked up again later in
the same turn, the count stays pending. A later end-of-turn observation of that object then confirms or withdraws
it. A confirmed count also confirms the pending counts of *different* steps before it: the sequence reached a later
step. Pending repeats of the same step stay pending, because seeing the third place-back says nothing about the
first two. In a CPU check of task 2 that rule would have confirmed two unseen repeats and fired a wrong S5b. Each
counted step records `confirmed_by`: `obs` or `vdm` when an observation confirmed it, `later_step` when only a
later step's observation did (it was never seen itself). The progress line says how many counted steps are still unconfirmed and how many were confirmed only by a
later step. The turn log has `confirmed_by` per step and `state()` has `later_step_confirmations`.

### Signals (estimated)

- S1 expectation violation: an expected effect of this turn contradicted by geometry, the gripper or the VDM
  (e.g. `inhand` expected but the gripper is empty, or the object is not where it was put down), or a drop while
  holding. The failed call is named.
- S2 progress stall: as for `bg_oracle`, on the estimated progress.
- S4 uncertain: a goal predicate of the last counted step or of the next steps has 0.3 <= P <= 0.7, or rests only on
  memory / expectation / prior not re-observed for `stale_turns` (2) turns. Suggests re-observing (move the arm away,
  look again).
- S5a / S5b: as for `bg_oracle`, on the estimated progress, but neither fires while progress is unknown, any of
  those goal predicates is uncertain (the S4 condition), or **any counted step is still pending**. A wrong
  completion signal could otherwise mislead the model. The current truth of earlier counted steps is not
  re-checked: later steps may undo them on purpose (the swap task moves bowl_A off plate_C again). Their check is
  the evidence at the time they were counted.
- S3 is out of scope.

### Prompt text

Same layout as `bg_oracle` (Progress / Objects / Events / Signals) with a title saying everything is an estimate, P
and source after every relation (`on plate_B 0.97 obs`, `in gripper 0.70 exp`), `not seen since tK` for objects not
seen this turn, and a `Violations:` line (last 3) before `Signals:`. When every step is counted but the estimate is
uncertain (S5 suppressed), the Progress line says `all steps counted, but NOT all confirmed` instead of `all steps
estimated complete`, so the wording does not invite a FINISH that S5b would not back. The budget rule is the same as `bg_oracle`;
Violations, like Progress and Signals, is never cut.

### Running `bg_est`

```bash
uv run --no-sync --active capx/envs/launch.py \
    --config-path env_configs/capbg_baseline/libero_mem/task_06_swap_bowls.yaml \
    --memory-mode bg_est --output-dir outputs/capbg_bg_est/task_06_swap_bowls ...  # model flags as above
```

The SAM3 server of the config (`127.0.0.1:8114`) must be up: `bg_est` calls it itself, once per category per
perception. The goal is parsed by the coding model (`--model`, `--server-url`) and the verification VDM uses
`--visual-differencing-model`. Options (CLI flag or YAML key; CLI wins). They only exist when `memory_mode` is
`bg_est`:

| Key | Default | Meaning |
| --- | --- | --- |
| `memory_signals` | `S1,S2,S4,S5` | Signals (`none` turns them off). S1 and S4 exist only for `bg_est`. |
| `memory_est_perception` | `sam3` | `sam3`, or `sim_fake_for_tests` (simulator poses + noise; tests and CPU checks only). Any other value is an error, so the fake detector is never selected by accident. When it is used, every `memory_state.perception` / `memory_est.perception` in `all_responses.json` says `sim_fake_for_tests (FAKE ...)`, and `summaries.txt` gets a `NOT A VALID EVALUATION` line. |
| `memory_est_goal_source` | `llm` | `llm`, or `bddl` (diagnostics: BDDL goal with sim names mapped to turn-0 aliases; logged as `goal.source: bddl`). |
| `memory_est_max_categories` | 5 | Object categories taken from the task language. |
| `memory_est_gate_dist` | 0.10 | Data-association gate (m). |
| `memory_est_verify` | true | One verification VDM call per turn. |
| `memory_est_shadow` | true | Log the oracle shadow (needs the LIBERO-Mem env; logs only). |
| `memory_est_goal_model` / `memory_est_goal_server_url` | coding model / server | Model for goal parsing (text only). |

`memory_max_chars`, `memory_max_finish_rejections` and `memory_in_initial_prompt` work as for `bg_oracle`. A turn
that ran no code (`truncated_skip`) is still observed, so the text keeps the turn number current. It never
fires S1 or S2, and S2 then compares the next executed turn with the last executed one (same rule as `bg_oracle`).

**Harness integration.** `CodeExecutionEnvBase.api_call_wrapper` (default None: functions are bound as before)
wraps the API functions bound into the code sandbox. `bg_est` sets it to the record-only hook and every trial
resets it, because envs are reused across trials. `bg_est` reads the robot observation through
`env.low_level_env.get_observation()` and the step counter `_sim_step_count`. The task language comes from
`handle.task_language`. Memory is created after the VDM query settings, which changes nothing for the other modes.

**Logs** (`all_responses.json`): every entry has `memory_state`. For `bg_est` that is `estimator.state()` plus
`perception`, `over_budget`, `uncertain`, `suppress_completion`, `calls` and `shadow_totals`. `calls` holds
`goal_parse` with its prompt / completion tokens, `verify_vdm` with its tokens, and `perception` (detector calls:
SAM3 requests). Every entry also has `memory_est`:
- `est`: this turn's estimator record: hook `records`, `expectations`, `detections`, `new_tracks`,
  `unmatched_tracks`, `rematched`, `hypotheses`, `verify` (reply, answers), `conflicts`, `events`, `violations`,
  `uncertain`, `progress`, `pending`, `confirmed_by`, `rolled_back`, `perception`.
- `goal` (initial entry): the parsed goal, attempts, errors, raw replies.
- `shadow` (**evaluation only, never in a prompt**; `capx/belief/shadow.py`):
  - `mapping`: alias -> sim object, per category, by Hungarian on position.
  - `aliases_swapped_vs_t0` and `identity_swap_events`: aliases now mapped to a different object than at turn 0,
    and those that changed since the previous turn.
  - `goal_pred_correct` / `goal_pred_total` / `goal_pred_wrong`: goal predicates, estimate P > 0.5 vs the oracle
    graph, aliases read with the turn-0 mapping.
  - `est_done` / `oracle_done` / `step_error`; `oracle_complete`.
  - `signals`: each fired signal judged against the truth. S1 is right if the oracle also contradicts the
    expectation. S4 is right if a flagged predicate really was wrong, or a count was unconfirmed. S5b is right if
    the oracle says complete. S2 is right if the oracle made no progress either.
  - `finish_check`: an S5a rejection, right if the oracle was not complete.
  - The initial entry adds `goal_match` (parsed goal == BDDL goal under the turn-0 mapping) and `oracle_goal`.
  - `memory_state.shadow_totals` accumulates all of the above per trial, including
    `s5_suppressed_while_complete`.

**Calibration (measured on LIBERO-Mem task 6, CPU):** `robot_cartesian_pos` is 0.108 m behind the fingertip centre
along the approach axis. The estimator uses the fingertip point (`perception.TCP_OFFSET`). Closing on nothing reads
about 0.015. A rim grasp on the bowl reads 0.11 after the close and about 0.044 once lifted, so `grasp_threshold` is
0.025. Among objects within `grasp_radius` of the fingertips, the highest is taken as grasped: a rim grasp is about
as close to the plate under the bowl as to the bowl. The held object's offset from the fingertips is measured at
the grasp.

### Known limitations

- **Perception errors.** A missed detection keeps the old position (`mem`). After `stale_turns` it becomes S4 and
  blocks S5. A false detection of a tracked category is re-matched to a leftover track within `rematch_dist`
  first, so it can pull a track away from an occluded object. Only the agentview camera is used, so objects
  under or behind the arm are often missed while it is over them.
- **Identity swaps.** Identity rests on hook predictions and distance. Two same-shape objects moved without hooked
  calls (or a grasp attributed to the wrong object) can swap names, and nothing corrects it later. The shadow
  counts these (`identity_swap_events`). The grasped object is assumed to be the highest tracked object near the
  fingertips.
- **Categories** come from a fixed vocabulary. Region targets such as "the center of the table" never hold, so S5
  stays suppressed for task 8 / 9 style goals.
- **Repeats need hooks.** A pick-and-place-back that does not go through the hooked API calls is invisible: the end
  state does not change. A hook count without end-of-turn evidence stays pending, which blocks S5.
- **CPU check only:** the SAM3 path (`Sam3PerceptionSource`) is wired to cap-x's SAM3 client but has not run
  against a real SAM3 server here (no GPU). Its depth lifting is unit-tested on synthetic data.

### Fake perception (tests and CPU only)

`SimPerceptionSource` turns simulator poses into category-only detections, with Gaussian noise (1 cm), 10 % misses
and 50 % misses under the gripper. It prints a `perception=sim_fake` banner when created. The estimator records its perception source name in
`state()` and in every turn log (`perception`). It exists for tests and CPU
checks without SAM3 and must never be used for an evaluation run.

## Estimated Belief Graph v2 (`bg_est2`)

`bg_est2` keeps `bg_est`'s inputs (cameras, robot state, API calls, VDM, task language; no simulator state) and
its tracks, data association, hooks and step counting, and changes how relations are observed and how the
code agent takes part. Design: `/outputs/cap-bg/tasks/bg-est2-design.md` (prompt texts M2–M5 there are used
verbatim, `capx/belief/prompts_v2.py`). `bg_est` is unchanged and can still be run for comparison.

| Module | Role |
| --- | --- |
| `som.py` | Marks: letters A, B, … for objects, numbers 1, 2, … for supports (plates, baskets), fixed per trial and in alias order (aliases go from the image left = robot base −y). Drawn at each track's projected center. A track not detected in this image gets no mark. |
| `observe.py` | Statement format `(on bowl_A plate_B)`, `(in cream_cheese_A basket_A)`, `(at basket_A center)`, `(inhand bowl_B)`, `(handempty)`. Lenient parser of the `Observe:` line (order, spaces, case, `true/false`), `Notes:` line, Notes flags (tilted / fallen / wrong mark). |
| `prompts_v2.py` | M2 (initial Observe), M3 (goal), M4 (declaration rules), M5 (turn Observe). |
| `declare.py` | Parses `# Subtask: op(args)` / `# Effect: (pred) a>b \| ...` from the first two lines of the block; checks them against the API calls. |
| `subtasks.py` | Operators pick / place / put_in / place_region, expansion of goal steps, statuses. |
| `estimator2.py` | `BeliefEstimatorV2` (a `BeliefEstimator` subclass). |
| `memory2.py` | `BgEst2Memory` (`memory_mode: bg_est2`), `belief_trace.jsonl`. |
| `shadow.py` | `OracleShadowV2` (evaluation logs only). |

### Per trial and per turn

- **Start.** Detection and aliases as in `bg_est`. **M2**: one marked image, every object × support relation
  (most likely first by geometry) and every object on the table, at most 20. **M3** (goal model): the scene
  as seen in the image — left/right in image terms (base −y is image left), distance from the camera (base x),
  "empty" / "holds X" from M2 — and a region line when the instruction names one (`center`). Steps list only
  newly true predicates; a reply with cumulative steps is normalized (a predicate already true before its step
  is dropped when the step has a new one; a step with none new, a put-back or repeat, is kept).
- **M4** is appended to the first prompt and to every decision prompt (bg_est2 only).
- **Turn end.** The harness passes the block that ran. A valid declaration (op ∈ pick, place, put_in,
  place_region, look; known names) whose operator API ran (pick: `close_gripper`; place*: `open_gripper`)
  turns its Effects into expectations (P 0.7 / 0.3). No declaration or a malformed one → `bg_est`'s hook
  inference (`declared: false`). A declaration the calls contradict (place declared, the gripper opened above
  another tracked support; pick declared, another object grasped) is dropped and shown as `IGNORED`. A valid
  declaration also names the grasped object when several are within reach (a basket with the cheese inside).
- **M5**: images before / now (marks only for objects detected now), the declaration, and at most
  `memory_est_observe_max_statements` (10) statements: declared Effects, the declared / moved objects'
  relations (target, previous support, table), goal-relevant predicates, unconfirmed counted steps, then where
  the goal objects are believed to be. Plates are never asked about.
- **Fusion** per key: robot state (inhand, handempty, above(gripper, t), lifted, P 0.97, source `robot`) >
  Observe 1 / 0 (P 0.9 / 0.1, `vdm`) > geometry (only when Observe failed, or for a key with no belief yet)
  > expectation > memory. `?` keeps the memory. A relation set true lowers the object's other on / in / inhand
  relations not observed now (regions overlap supports and are left alone). Observe on / in = 1 for objects
  more than 2 support radii apart → P 0.5 + S4. Notes saying an object is tilted / fallen → its observed
  "on a support" relations P 0.5; "wrong mark" → all its observed relations P 0.5; S4 quotes the note. A reply
  with no readable statement → geometry only (the `bg_est` way), `Observe (tN): failed` in the block.
- **Steps** are counted from hook snapshots as in `bg_est`; a count is confirmed only by an observation (Observe
  or robot) with P ≥ 0.7, stays pending on declaration + API only, and is withdrawn (S1) on Observe 0.
- **Subtasks.** pick = grasped and lifted (robot); place / put_in / place_region = released after a lift and
  judged on the target relation at turn end: 1 → done, 0 → failed (S1), ? → pending (judged again later if the
  object did not move). A region (`center`) is at(o, r) from the distance to the region center: where the
  front camera's optical axis meets the table (shown in the Objects line), radius 0.10 m.
- **Signals.** S1: failed subtask ("place(bowl_B, plate_B) failed: bowl_B is on table. Retry the place, not the
  whole task"), declared Effect contradicted, grasp missed / object dropped, count withdrawn. S2: remaining
  steps unchanged **and** no subtask done / pending this turn. S3: the next planned subtask's precondition is
  confidently false (in practice: the gripper holds another object). S4: a goal-relevant key `?` two turns in a
  row, a geometric anomaly, a Notes flag, a count unconfirmed for 2 turns. S5b (oracle wording) and S5a are
  suppressed while any count is pending or anything is uncertain.
- **Event frames** (`memory_est_event_frames`, default off; needs recorded frames): the recorded frame right after
  each gripper close / open gets an extra Observe on that object (at most 4 per turn); its answers fill turn-end
  `?` when the gripper did not close again afterwards.

### Prompt block

Turn 0 (first prompt) and later turns (decision prompt, after the VDM description, before the REGENERATE /
FINISH instructions; M4 follows at the very end):

```
Belief graph (turn 2, ESTIMATED; names match the marks; xyz in the robot base frame, m: x away from the robot, y to the robot's left):
Subtask (declared): place(bowl_B, plate_B)
Effect (declared): (on bowl_B plate_B) 0>1 | (inhand bowl_B) 1>0
Observe (t2): (on bowl_B plate_B) ? | (inhand bowl_B) ? | (on bowl_B plate_C) ? | (on bowl_B table) ? | (on bowl_A plate_A) 1
Belief: (on bowl_A plate_A) 0.90 vdm | (on bowl_B plate_B) 0.70 exp | (on bowl_A plate_C) 0.10 mem | (handempty) 0.97 robot
Delta: step 2/3 done | next: (on bowl_A plate_C) | remaining 1 | 1 counted step(s) not yet confirmed by the camera
Subtasks: pick(bowl_B, plate_C) done -> place(bowl_B, plate_B) pending (not confirmed by the camera) | next: pick(bowl_A, plate_A) -> place(bowl_A, plate_C)
Objects: bowl_A at (0.43, -0.13, 0.02) | bowl_B at (0.68, 0.00, 0.03), not seen since t1 | plate_A at (0.46, -0.14, -0.01) | ...
Signals: none
```

Over `memory_max_chars`: Belief items are dropped from the end, then the Objects line, then the Observe line is
shortened; title, Subtask, Effect, Delta, Subtasks and Signals are never cut.

### Logs

- `all_responses.json`: as `bg_est` (`memory_*`, `memory_est` with `est`, `shadow`) plus
  `memory_est.cot_record` = `{turn, Subtask, Effect, declared, Observe, Notes, Belief, Delta, Subtasks, Signals}`.
- `<trial_dir>/belief_trace.jsonl`: one line at the start, per turn end and per event-frame Observe: `nodes`
  (category, mark, pos, size, last_seen, pixel, flag), `robot` (eef, gripper, handempty, above, holding,
  lifted), `keys` (per relation: P, source, obs, observe answer, last_seen_turn, geom {dz, d_xy, r}, `shadow` =
  simulator truth), `goal` (+ region centers), `steps` (status, by, turn), `subtasks`, `plan`, `declaration`,
  `observe` (statements, reply, parsed, prompt text), `cot`, `signals`, `est`, `shadow`. Written to
  `<output_dir>/belief_trace_trial_NN.jsonl` while the trial runs and copied into the trial directory.
- Shadow totals (`memory_state.shadow_totals`): `bg_est`'s plus `observe` (per predicate: answers 1 / 0 with
  [n, right], `?`, missing), `observe_fail`, `declared` / `declared_valid` / `declared_dropped` /
  `turns_with_code`, `effects_applied` / `effects_right`, `subtasks_judged` / `subtasks_right`, `S3`; start log
  `goal_match_normalized` (both goals reduced to newly true predicates per step).

### Running `bg_est2`

Same as `bg_est` with `--memory-mode bg_est2`. Extra keys:

| Key | Default | Meaning |
| --- | --- | --- |
| `memory_signals` | `S1,S2,S3,S4,S5` | S3 exists only here. |
| `memory_est_verify` | true | Switches the Observe VDM (M2 / M5), which replaces `bg_est`'s verification VDM. Off: geometry only. |
| `memory_est_observe_max_statements` | 10 | Statements per turn-end Observe. |
| `memory_est_event_frames` | false | Extra Observe on recorded frames right after gripper close / open. |

`memory_est_perception`, `memory_est_goal_source`, `memory_est_goal_model`, `memory_est_shadow`,
`memory_est_gate_dist`, `memory_est_max_categories` work as for `bg_est`. Extra model calls per trial: one M2 and
one M3, then one M5 per turn (event frames: up to 4 more).

Offline Observe accuracy (`scripts/eval_observe.py`): `scenes` makes labelled LIBERO-Mem scenes on CPU (needs the
simulator, no keys); `query` sends them to the VDM as M5 prompts (`OBSERVE_VDM_URL`, `OBSERVE_VDM_MODEL`,
`OBSERVE_VDM_API_KEY`) and writes `results.jsonl`, `table.md` (accuracy per predicate × condition × truth, `?`
rate). `LIBERO_MEM_ROOT` points scene making at another LIBERO-Mem checkout (for its init states).

### Known limitations (v2)

- The VDM is the main observer of relations; its accuracy on marked LIBERO images is not yet measured
  (`eval_observe` first). A wrong but confident Observe 1 / 0 overrides geometry; only the 2-radii anomaly rule
  and Notes catch it.
- Region centers are an estimate (the camera axis on the table), not the BDDL region; at(o, center) is judged by
  the VDM or by distance to that point.
- Declarations are trusted when the API calls do not contradict them; a code agent that declares a target and
  drives elsewhere above no tracked support is not caught until Observe.
- Marks sit at estimated centers; a stale track (not detected) gets no mark, so the VDM must answer `?`.
- Event frames are wired (frame index from the sim step and the recording rate) but untested on real frames.

## Privileged information

With `privileged: false` the generated code sees no ground-truth task state: LIBERO-Mem's subgoal tracker is
only in `info["memory"]` (logged per turn in `all_responses.json`), and the sandbox has no `env` global. The
sandbox runs in-process, so this is not full isolation (an API function's `__self__` or `APIS` still reaches the
env); `analyze_pilot.py` flags trials whose code touches such state.
