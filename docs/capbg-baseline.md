# cap-bg Baseline (CaP-Agent0, ensemble off)

The cap-bg baseline uses the CaP-Agent0 settings (`env_configs/libero/franka_libero_cap_agent0.yaml`) with the
parallel ensemble **off**. Image differencing (VDM) and multi-turn are on. The CaP-Agent0 YAML itself is left
unchanged as the record of the paper settings.

## Configs

All baseline configs are generated by `scripts/gen_capbg_baseline_configs.py`. Do not edit them by hand. Change
the script, then rerun it:

```bash
python scripts/gen_capbg_baseline_configs.py          # writes env_configs/capbg_baseline/
python scripts/gen_capbg_baseline_configs.py --check  # exit 1 if a file is stale (also run by tests/)
```

| Config | Benchmark |
| --- | --- |
| `env_configs/capbg_baseline/libero_pro/franka_libero_object_swap_0.yaml` | LIBERO-PRO `libero_object_swap` task 0 (same task as CaP-Agent0) |
| `env_configs/capbg_baseline/libero_mem/task_<NN>_<slug>.yaml` | LIBERO-Mem tasks 0–9 (0-based `task_id`; e.g. `task_06_swap_bowls` = `KITCHEN_SCENE1_7`) |

Every config sets these values explicitly instead of relying on defaults:

| Key | Value |
| --- | --- |
| `use_parallel_ensemble`, `use_multimodel` | `false` |
| `use_img_differencing` | `true` |
| `use_visual_feedback`, `use_video_differencing`, `use_wrist_camera` | `false` |
| `record_video`, `save_multiturn_prompts` | `true` |
| `max_tokens` | `32768` (coding model and VDM; upstream default 20480, see below) |
| `prompt`, `multi_turn_prompt` | copied verbatim from the CaP-Agent0 YAML |
| `apis` | `FrankaLiberoApiReducedSkillLibrary` |
| `api_servers` | pyroki 8116, contact_graspnet 8115, sam3 8114 (same as CaP-Agent0) |
| low-level env | `privileged: false`, `max_steps: 8000`, `control_freq: 20` |
| `trials` / `num_workers` | 50 / 10 (override with `--total-trials` / `--num-workers`) |

`FrankaLiberoApiReducedSkillLibrary` also works with `FrankaLiberoMemEnv`, because it is a `FrankaLiberoEnv`
subclass with the same cameras and control methods. The API only uses `get_observation` and
`move_to_joints_*`. Its SAM3, GraspNet, pyroki and Molmo clients are HTTP clients, so they need no server when
the API is created. Each server only has to be up when the generated code calls it.

**`max_tokens`:** the YAML `max_tokens` key sets the per-reply token limit for both the coding model and the
VDM; `--max-tokens` on the CLI overrides it, and without either the original default 20480 applies. The
baseline uses 32768, not 20480: on Nebius reasoning tokens count against the limit, and in the LIBERO-Mem 10×5
pilot (`max_tokens` 20480) Kimi-K3 replies hit it often (17 replies ran with an unclosed code fence and one
ended a trial with an infinite loop). Checked on Nebius (2026-10-30): both Kimi-K3 and Qwen3.8-27B accept it, and
a long Kimi-K3 reply ran to exactly 32768 completion tokens before stopping with `finish_reason: length`. Nebius
does not reject larger values either, so acceptance alone says nothing about the server-side cap.

**Ensemble ablation:** use the same configs and turn the ensemble on from the CLI with
`--use-parallel-ensemble True --use-multimodel True`.

## venvs

The `libero`, `libero-mem` and `molmo` (vllm) extras are mutually exclusive, so use one venv for each:

```bash
uv venv .venv-libero --python 3.12 && source .venv-libero/bin/activate
uv sync --active --extra libero --extra contactgraspnet          # LIBERO-PRO

uv venv .venv-libero-mem --python 3.12 && source .venv-libero-mem/bin/activate
uv sync --active --extra libero-mem --extra contactgraspnet      # LIBERO-Mem

uv venv .venv-molmo --python 3.12 && source .venv-molmo/bin/activate
uv sync --active --extra molmo                                   # Molmo2-8B vLLM server only
```

## Molmo server (start it separately)

The API's `point_prompt_molmo` calls a Molmo2-8B vLLM server at `http://127.0.0.1:8122/v1`. The molmo extra
cannot be installed in the libero venvs, so the server is not in `api_servers`. Start it from `.venv-molmo`
before launching:

```bash
.venv-molmo/bin/python capx/serving/vllm_server.py --model allenai/Molmo2-8B --port 8122 \
    --max-model-len 16384 --max-num-batched-tokens 16384 --log-file logs/molmo.log &
```

One image is about 8134 tokens, so vLLM fails to start with its default limits. Keep the two `16384` flags. Use
`--gpu-memory-utilization` if the server shares the GPU with SAM3 and GraspNet.

## Models

Pass the coding model and the VDM model on the CLI. Keep keys in environment variables, not in files or in logs
you commit. Example with Nebius (OpenAI-compatible chat-completions endpoint):

```bash
--model moonshotai/Kimi-K3 --server-url "$NEBIUS_SERVER_URL" --api-key "$NEBIUS_API_KEY" \
--visual-differencing-model Qwen/Qwen3.8-27B \
--visual-differencing-model-server-url "$NEBIUS_SERVER_URL" --visual-differencing-model-api-key "$NEBIUS_API_KEY"
```

`$NEBIUS_SERVER_URL` is the full chat-completions URL (`.../v1/chat/completions`), like the default
`http://127.0.0.1:8110/chat/completions`.

> **Warning:** VDM runs only if `--visual-differencing-model` is in `VLM_MODELS` in `capx/llm/client.py`.
> Otherwise image differencing is **silently skipped** even with `use_img_differencing: true`. Add new model IDs
> there first. `moonshotai/Kimi-K3` and `Qwen/Qwen3.8-27B` are already listed.

## Rendering

- **LIBERO-PRO:** on GPU nodes, `MUJOCO_GL=egl` works (it is also the default set by `launch.py`).
- **LIBERO-Mem:** on GPU nodes, use `MUJOCO_GL=egl PYOPENGL_PLATFORM=egl`. LIBERO-Mem's robosuite 1.4.1 EGL
  context fails with PyOpenGL 3.1.6 on Python 3.12; `capx.envs.simulators.libero_mem` patches it on import
  (`patch_robosuite_egl_context`). Without a GPU, use OSMesa with `NUMBA_DISABLE_JIT=1` (see
  `docs/memory-benchmarks.md`): `MUJOCO_GL=osmesa PYOPENGL_PLATFORM=osmesa NUMBA_DISABLE_JIT=1`. That path is
  much slower (CPU rendering, no JIT) and is meant for smoke checks, not evaluation.

## Trial timeout

Each trial attempt has a wall-clock budget (`trial_timeout_s`, default 1000 s, counted from after `env.reset()`)
and is retried on timeout up to
`max_trial_retries` times (default 3). Both can be set in the YAML or on the CLI (`--trial-timeout-s`,
`--max-trial-retries`). For baselines, use `--max-trial-retries 1`: with an enforced timeout, a retry re-rolls a
slow trial and biases the success rate up. The budget includes model latency, so a timeout mixes slow API calls
with task failure; report timeouts separately.

Known limitations of the SIGALRM timeout (the robust fix is killing the worker process from outside):

- After the deadline the alarm re-fires every 2 s, so it can interrupt cleanup code (`finally` blocks) in the trial.
- Generated code that loops forever inside a bare `except:` can still swallow every alarm.

A timed-out trial still saves its video (per-turn videos plus `video_combined.mp4`, including the turn that was
cut off) from the frames recorded so far; if no frames were recorded, no video is written.

## Init states

LIBERO-Mem tasks 0, 6, 7 and 8 use upstream init states; tasks 1, 2, 3, 4, 5 and 9 use the generated sets in
`capx/integrations/libero_mem/init_states/` (see `docs/memory-benchmarks.md`). Each trial records `init_source`, and
`analyze_pilot.py` reports success per init source, so report the two groups separately. Regenerate with
`MUJOCO_GL=osmesa PYOPENGL_PLATFORM=osmesa NUMBA_DISABLE_JIT=1 python scripts/gen_libero_mem_init_states.py --tasks 1 2 3 4 5 9 --num 50`
(about 4 GB RAM per process; reruns with the same seed give the same states).

## Step cap

`max_steps` in the low-level env config is the step budget; the robosuite horizon is built from the same value.
`FrankaLiberoEnv` (and LIBERO-Mem) raises `EpisodeTruncated` (a BaseException, so generated code cannot swallow
it) before a sim step would exceed it. The sandbox stops the code, `env.step` reports `truncated` from the env's
own step count, and the trial ends with a final `all_responses.json` entry
`{"decision": "truncated", "reason": "step_cap"}` and `Truncated: True` in `summary.txt`.

## Multi-turn decisions

The original harness treated any reply without the literal `REGENERATE` as FINISH, so new code written without
the keyword (or in Kimi-K3's raw tool-call format) was dropped and the trial ended. Replies are now classified
by `parse_multi_turn_decision` in this order: `REGENERATE` keyword (original behavior, with the code after it
normalized the same way); a fenced code block (also an unclosed one cut off by the token limit) or a tool-call
`code` argument means regenerate, unless `FINISH` comes after the last code (e.g. quoting code that already
ran), which finishes so that code is not run twice; `FINISH` with no code means finish; an empty reply is
queried once more and finishes if it is empty again; anything else finishes. Each multi-turn entry in
`all_responses.json` records `decision_source`, `decision_flags` (`finish_with_code`, `finish_after_code`,
`unclosed_fence`) and `legacy_decision`, so runs can report format violations and how often the decision
differs from the original parser. Every model reply entry also records `finish_reason` and `usage`:
`finish_reason: length` means the reply hit `max_tokens`, and on Nebius reasoning tokens count against it (a
reply cut during reasoning comes back with empty content).

A reply with `finish_reason: length` is never executed or parsed (the initial code and multi-turn decisions
alike): the same prompt is queried once more, and the entry records `truncation: retry` and the first reply's
`truncated_first_usage`. If the second reply is cut off too (`truncation: skip`, `decision_source:
truncated_skip`), no code runs; the next turn runs nothing and its decision prompt shows "Your previous reply was
cut off by the output token limit and was not executed. Reply more concisely." in place of the console stderr.
That turn counts toward the turn limit, so repeated truncation cannot loop forever. The `unclosed_fence` flag
therefore only appears when the API reports no `finish_reason` or a reply ends in an open fence for another
reason.

**Goal in decision prompts (differs from the original cap-x):** the original harness filled
`{libero_environment_goal}` only in the first prompt, so every decision prompt said `Goal:
{libero_environment_goal}`. `_patch_libero_goal` now also fills the env's own prompt (from the unfilled template,
restored on `reset()`), so all memory modes see the same goal line in every prompt; the first prompt and the VDM
task description are unchanged.

## Memory conditions (`memory_mode`)

The same baseline configs run every memory condition. Choose the condition on the CLI and leave the generated
YAMLs as they are (`memory_mode` is not in them, so it defaults to `none`):

| `--memory-mode` | What the decision prompt gets |
| --- | --- |
| `none` (default) | The cap-x baseline. Every prompt is byte-identical to the harness before memory existed (`tests/test_memory_mode.py` checks this against a recorded fixture). |
| `vdm_history` | The VDM descriptions of all previous turns, as `turn k: ...` (unstructured text memory). The current turn's description is already in the VDM block, so the history leaves it out. |
| `bg_oracle` | A Belief Graph built from LIBERO-Mem **simulator ground truth** (`capx/belief/`): progress over the BDDL goal steps, object positions and supports, location-change events, plus the S2 / S5 signals below. This is an upper bound, not a deployable method. |

The memory block goes after the VDM description and before the REGENERATE / FINISH instructions. Options (CLI
flag or YAML key of the same name; CLI wins):

| Key | Default | Meaning |
| --- | --- | --- |
| `memory_max_chars` | 3000 | Budget of the memory block. `vdm_history` drops the oldest turns. `bg_oracle` drops the oldest events, then shortens and finally leaves out the objects line, but never cuts the Progress and Signals lines (`memory_state.over_budget` marks when those alone exceed the budget). |
| `memory_signals` | `S2,S5` | `bg_oracle` signals (`none` turns them off). S2: an executed turn left the number of remaining steps unchanged. The prompt says "no progress this turn" and asks the model to rethink. S5b: every step is verified complete. The prompt says so, and the model still decides FINISH (the harness never ends a trial by itself). S5a: a FINISH while steps remain is rejected and the same prompt is asked again with the reply and the remaining steps appended. That answer stands. |
| `memory_max_finish_rejections` | 1 | S5a rejections per trial. |
| `memory_in_initial_prompt` | true | `bg_oracle`: also append the turn-0 graph to the first code-generation prompt. |

Example (LIBERO-Mem task 6, oracle condition):

```bash
uv run --no-sync --active capx/envs/launch.py \
    --config-path env_configs/capbg_baseline/libero_mem/task_06_swap_bowls.yaml \
    --memory-mode bg_oracle --output-dir outputs/capbg_bg_oracle/task_06_swap_bowls ...  # model flags as above
```

Use a separate `--output-dir` per condition. The generated YAMLs all point to the same default directory.

A turn that ran no code (`truncated_skip`) still updates the memory, so its text keeps the current turn
number, but it never fires S2. The next executed turn is compared with the last executed one.

Logs in `all_responses.json`: the initial entry has `memory_mode`, `memory_initial_text` (exactly what was
appended to the first prompt, or null) and `memory_state`. Every decision entry has `memory_mode`, `memory_text`
(exactly what the prompt got), `memory_signals` (`[{id, reason, text}]`), `memory_state` (`bg_oracle`: `done`,
`remaining`, `overshot`, `known`, `over_budget`) and `s5_rejected`. A rejected FINISH also records `s5_rejection`,
`s5_first_reply` (the rejected reply with its parse metadata) and `s5_rejection_prompt_tail` (the two appended
messages). The entry's decision fields describe the second answer.

`bg_oracle` reads ground truth through the harness's own `env.low_level_env` reference. Generated code still
gets no memory or env object (exposing a belief API to code is out of scope).

## Privileged information

With `privileged: false` the generated code sees no ground-truth task state: LIBERO-Mem's subgoal tracker is
only in `info["memory"]` (logged per turn in `all_responses.json`), and the sandbox has no `env` global. The
sandbox runs in-process, so this is not full isolation (an API function's `__self__` or `APIS` still reaches the
env); `analyze_pilot.py` flags trials whose code touches such state.

## Running on kubectl

GPU pods are killed after 30 minutes without GPU use. Do `uv sync`, submodule checkout and other CPU-only work
in a CPU pod, and only start the GPU pod when you are ready to run.

LIBERO-Mem (Molmo server already running):

```bash
source .venv-libero-mem/bin/activate
MUJOCO_GL=egl PYOPENGL_PLATFORM=egl \
uv run --no-sync --active capx/envs/launch.py \
    --config-path env_configs/capbg_baseline/libero_mem/task_06_swap_bowls.yaml \
    --model moonshotai/Kimi-K3 --server-url "$NEBIUS_SERVER_URL" --api-key "$NEBIUS_API_KEY" \
    --visual-differencing-model Qwen/Qwen3.8-27B \
    --visual-differencing-model-server-url "$NEBIUS_SERVER_URL" --visual-differencing-model-api-key "$NEBIUS_API_KEY"
```

LIBERO-PRO: same command from `.venv-libero` with `MUJOCO_GL=egl` and
`--config-path env_configs/capbg_baseline/libero_pro/franka_libero_object_swap_0.yaml`.

CPU check without a GPU (low-level env creation, reset and random steps; no servers needed):

```bash
CUDA_VISIBLE_DEVICES="" MUJOCO_GL=osmesa PYOPENGL_PLATFORM=osmesa NUMBA_DISABLE_JIT=1 \
uv run --no-sync python scripts/bench_smoke.py \
    --config-path env_configs/capbg_baseline/libero_mem/task_06_swap_bowls.yaml --out-dir outputs/bench_smoke/capbg_mem_6
```
